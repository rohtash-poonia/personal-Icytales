# Project repair implementation plan

User-authorized full repair of existing Next.js JavaScript, Express, MongoDB and Mongoose functionality. Preserve the stack and existing user changes. No production database writes, destructive migrations, deployment, push or fabricated integration success.

## Design

Use the existing Product and Order schemas as the shared API contract, with backward-compatible adapters for cart data. All environments enforce authentication and backend authorization. Validate inputs, compute prices on the server, enforce stock atomically, and make payment state truthful. COD is supported; card/UPI require a verified provider and remain explicitly unavailable until configured. Keep the existing visual structure and safely replace references to missing assets without restoring user-deleted files.

## Tasks

- [x] T1 Backend authentication, authorization, validation, sessions, errors, CORS, uploads, rate limits and regression tests.
- [x] T2 Database/order correctness: trusted prices, stock, transactions, idempotency, status consistency, pagination, statistics and tests.
- [x] T3 Storefront API catalog, details, shared persisted cart, checkout, session handling, API client and tests.
- [x] T4 Admin CRUD/status/block controls, truthful dashboard, loading/errors and mobile/accessibility fixes.
- [x] T5 Remaining content forms, navigation, missing assets, lint, dependencies, startup/deployment and documentation.
- [x] T6 Safe isolated database/API/frontend integration tests, lint, builds, security review and file-by-file report.

## Verification

Use meaningful failing regression tests before behavioral fixes. Use an isolated test database only; never connect tests to the real .env MongoDB URI. Record exact commands and outcomes. Run frontend lint/build, backend syntax/tests, API integration tests and dependency audit. Distinguish verified fixes, incomplete verification and external setup blockers.

## Decisions

Ruling: edit the user's current workspace with a pre-edit baseline, since backend and root configuration are outside the frontend Git repository and the user requests direct implementation. Cost if wrong: changes require comparison/reversal against the baseline; no user changes will be reset.
Ruling: do not require repeated design approval for the already authorized repairs; the user's explicit implementation instruction takes precedence over skill approval gates.
Ruling: do not invent payment-provider success or credentials; COD is the feasible purchase path, and online payment remains a documented external blocker.
